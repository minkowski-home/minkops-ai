## Regression against the October 13 build

The user reported 2–3-minute batches across parallel lanes on October 13. The comparison baseline is the last `staging` ancestor before midnight IST on October 14: **`150c5d6`**, authored October 13 at 23:45 IST. It contains desktop **0.6.10** and Bill Entry workflow **0.12.2**; current code contains desktop **0.9.0** and workflow **0.16.0**. This is a verified Git baseline, not proof of the exact installer the user ran. No October 13 Bill Entry task records were available in the current production database to replay that timing comparison.

**The `execution` settings dictionaries are exactly equal in that baseline and HEAD.** Both specify `gpt-6-luna`, `openai_hosted`, the same Python packages (`openpyxl`, `pymupdf`), instruction filename, resources and result path. There is no evidence here of a model-settings change causing the regression. The instruction file contents, output contract, execution stages and infrastructure did change.

The observed child AI stages were **319.9 s, 200.8 s and 441.6 s**, run serially: about **16 minutes** of stage time before inter-bill coordination/cleanup gaps. These stage timers include environment acquisition/preparation and related I/O, not pure model inference. B01-to-B02 AI-stage starts also included a **3-minute-40-second** gap after B01's AI stage ended. The lost wake-up delayed actual posting work about **18 minutes** after confirmation. These are distinct, measured regressions around the unchanged model configuration.

The remedy is to restore **memory-safe parallel execution**, fix the new dependency/notification boundary, remove snapshot data from status and mutable scheduling paths, and benchmark the expanded workflow against the old baseline. Re-enabling four lanes alone would leave the lost wake-up, slow confirmation, database scans and new staged work unresolved. The target 2–3-minute experience needs a same-input, same-context, same-review-policy comparison rather than a promise based solely on lane count.

## Root causes and durable fixes

P0 means work can remain stranded or a consequential action has an ambiguous outcome. P1 covers material correctness or responsiveness of the user experience. P2 covers resilience and operational enforcement.

## Earlier PC-presence issue belongs to the same review

The 0.9.0 companion updates presence through claim polls, which pause during job execution and receipt delivery. Discovery progress and archive polling did not refresh `last_seen_at`. The 16.4 MB completion submission repeatedly retried under its 45-second client timeout. Recorded claim gaps were 198.6 and 172.3 seconds while Tally remained available.

The local patch from the preceding task adds authenticated-activity presence, a lightweight busy-worker heartbeat, serialized archive refresh and a 120-second completion-upload budget. This is a useful mitigation, not a complete large-transfer architecture. For durable large snapshots, use a versioned, bounded, integrity-checked transfer path with explicit transfer progress and idempotent acceptance; compression must retain decoded-size limits. Presence must remain independent of execution leases. The API must be released before the companion relying on its new endpoint.

There is a further server-side coupling to address: `desktop.authenticate` holds `FOR NO KEY UPDATE` on the device until the request transaction ends. Other authenticated requests for that device, including the new heartbeat, can queue behind a slow receipt. Receipt transport authenticates before reading its streamed body. A separate client heartbeat timer alone therefore does not guarantee timely presence. Give presence a short, independent authenticated update path/storage and narrow business-operation lock scopes deliberately, while retaining revocation, ownership and attempt fences. Test a receipt slower than the offline threshold, concurrent heartbeat and revocation; do not simply remove authorization locks globally.

The preceding local patch also changes the batch summary when a pattern awaits confirmation. It does **not** fix the lost worker notification, timeout/idempotency boundary, task-local decision surface, oversized status DTO or navigation cache. None of these local changes has been rolled out during this review.

## Validation and boundaries

The isolated reproduction used the actual decision endpoint, profile release and dispatcher with a disposable migrated/seeded PostgreSQL database. After simulated worker drain, confirmation returned 200 and two bills became runnable, but generation/acknowledgement stayed `(11, 11)` and dispatch returned false with zero submissions. Adding a durable notification in that isolated database made dispatch submit once. No production state was changed by that reproduction and no provider session was started.

A separate production diagnostic used `EXPLAIN` plus two **read-only SELECTs**, each bounded by a 2.5-second statement timeout, to compare dependency lookup scope. The original lookup was cancelled at the limit; the queued-only variant completed in 517.517 ms. No production UPDATE, index creation or migration was run. The reported 88.2 MB is stored compressed config across 60 tenant runs, not the uncompressed JSON read by every query.

The earlier local patch passed 114 API tests, 130 JavaScript tests and a desktop build. Those results do not validate the additional proposed changes here. The live watch uses read-only database/cloud inspection and ordinary UI navigation; it does not repeat Confirm, start a replacement bill run, approve accounting proposals or write vouchers.

The supplier-action reproduction fetched the pinned company context and B03 proposal using a read-only transaction, then called the current creation and voucher gates in memory. The original printed place of supply rejected creation while voucher validation passed. Canonicalizing only that value accepted both gates and changed `supported_write(..., supplier=True)` from false to true. No production proposal or ledger was changed. This corrects the earlier description of B03 as a prepared creation decision: detection finished, but the UI did not actually offer the intended action.

## Implementation order and acceptance

1. **Restore liveness and reliable decisions:** shared runnable-transition notification, a short recovery interval, idempotent confirmation receipts and explicit blockers. Regression: confirm after complete worker shutdown; one dispatcher submission and no stranded runnable child.
2. **Remove expensive status/control work:** bounded SQL/public DTOs, small decision transaction, immutable snapshot references, fewer scheduling connections. Status payload target below 50 KB independent of discovery size; status and decision p95 below 1 second under the agreed representative load, excluding external model/native operations.
3. **Repair navigation and feedback:** shared scoped cache, cancellation/deduplication, no discovery probe for known Bill Entry, per-action pending/uncertain/success state, coherent task stages. Cached return navigation should render immediately without regressing stage; revalidation must not enable stale writes.
   Include canonical GST jurisdiction validation and visible decision-ineligibility reasons so the B03 creation scenario is actually testable; preserve the separate B02 policy/capability hold.
4. **Restore memory-safe execution and prove recovery:** remove the full-snapshot candidate/guard allocations that make concurrency expensive, measure setup/AI/validation/queue durations separately, and restore only capacity-tested parallel lanes. Compare with October 13 using identical bills, company scope and review policy; benchmark warm confirmed-pattern runs separately from first-time setup. Observe provider/session recovery. Test network loss, server commit after client timeout, worker crash, shared profile confirmation and concurrent Stop.
5. **Release and measure together:** deploy compatible API/migration before the desktop update, monitor queue ages and request/payload budgets, and repeat the B01/B02/B03 scenario end to end. “Finished” must mean a verified terminal outcome; an intentional supplier-creation or review decision must appear as input needed rather than an endless spinner.
